# 排班衝突檢核規則 R01–R22

## 系統對法規的立場

**本系統不對勞動基準法在居家服務業的適用方式表示法律見解。**

所有工時門檻、休息時間、七休一等參數皆存於 `OrgPolicy` 表，由機構自行設定，程式中沒有寫死任何數值。系統的角色是「依機構設定的規則提出警示並留下軌跡」，不是「認定某個排班是否合法」。

**上線前，本文件所列的所有預設值都必須由機構的人資或法務書面確認。**

## 引擎設計

`packages/shared/src/scheduling/` — **純函式，不碰 DB、不碰網路、不讀系統時鐘**。

同一份程式碼在兩處執行：

| 位置 | 用途 | 是否可信 |
|---|---|---|
| 前端（拖曳中） | 即時預覽，資料來自 React Query 快取，<5ms | ❌ 僅供顯示 |
| 後端（寫入交易內） | 強制執行 | ✅ 唯一真相 |

前端結果永不被信任。此外 DB 層有 `EXCLUDE USING gist` 排他約束兜底時間重疊 —— 這是唯一能擋住「兩位督導同時把同一位照服員排進重疊時段」的手段，因為應用層檢核在並行情況下會雙雙通過。

## 需要特別說明的三條規則

### R18 七休一 —— 為何用滑動視窗而非「連續上班天數」

勞基法 §36 的文字是「**每七日中**應有二日之休息」，不是「連續上班不得超過六日」。

正確算法：以候選日為中心，檢查**所有包含候選日的長度 7 視窗**，若任一視窗內 7 天全部有班則違規。

只數「連續上班天數」會漏掉這種情形：

```
8/01 8/02 8/03 [8/04] 8/05 8/06 8/07
 有   有   有   候選   有   有   有
```

候選日插在中間，前後各只有 3 天連續，但 8/01–8/07 這個七日視窗內每天都有班。

### R19 班距 —— 為何只是 WARN

勞基法 §34 的 11 小時輪班間隔是針對**輪班制**的規定。居家服務是否構成輪班制，在實務上有爭議。系統因此僅列為警示並在訊息中標註「居家服務是否適用有爭議」。

### R07 路程 —— 為何永遠不能 BLOCK

兩個原因：

1. **與 DB 約束不一致**。`ServiceVisit` 的 EXCLUDE 約束以純時間區間判定重疊，不含路程緩衝。若 R07 升級為 BLOCK，會出現「應用層擋下但 DB 允許」的矛盾狀態。
2. **它只是估算值**。Phase 1 不依賴任何付費地圖 API：有座標時用 haversine × 迂迴係數 ÷ 路況車速，缺座標時退回行政區鄰接表。這個精度不足以作為硬性阻擋的依據。

UI 必須把估算標示為「粗估」並顯示 confidence（依座標估算／依行政區粗估／資料不足）。

## ⚠️ 最大的法遵不確定性：趟間空檔是否為工時

居家服務照服員在兩趟服務之間的空檔，是否應計入工時？

這涉及「待命時間 vs 自由運用時間」以及「交通時間是否為工時」的界線，是長照產業長年未定的爭議，且不同勞檢見解可能不同。

**系統的處理方式：不表示立場，同時輸出三種算法。**

| 算法 | 定義 | 傾向 |
|---|---|---|
| `loose` | 僅服務時數加總 | 對機構最有利的解讀 |
| `strict` | 首班到末班的完整跨度，所有空檔計入 | 對勞工最有利的解讀 |
| `policy` | 空檔 ≤ `idleGapCountsAsWorkThresholdMinutes` 者計入 | 機構設定的折衷值（預設 60 分鐘） |

- 排班警示以 `policy` 值判定
- 訊息中同時附上另外兩種數值供督導判斷
- 照服員詳情頁與工時統計 API 三者並陳

**此參數的設定值屬於機構政策決定，需經人資或法務確認，並建議與勞資會議或工會溝通後為之。**

## 覆寫機制

- 只有具 `schedule:override` 權限的角色（管理者、督導）的覆寫才生效
- 行政人員即使在 API 請求中塞入 `overrideRuleIds` 也不會被採納
- **不可覆寫的 BLOCK 即使列入覆寫清單仍會擋下**
- 每次覆寫寫入 `AuditLog` 的 `OVERRIDE` 動作，記錄規則代號、理由、操作者、IP 與時間

這些軌跡在勞動檢查或申報稽核時是說明依據。

## 測試

`packages/shared/src/scheduling/rules/*.test.ts` — 每條規則至少 3 個測試案例，含邊界情形：

- 跨午夜、跨月、跨年
- 剛好相接的班次（半開區間）
- 已取消班次不計入
- 證照到期日當天
- 修改既有班次時不與自己比對

覆蓋率門檻 90%，由 CI 強制。
